The per-pipeline `schedule:` block on `DltPipelineComponent` (dag-tools#39, mfg-trace PR A1) skips a tick while a run of `<pipeline>_job` is queued or in progress. It finds those runs by **job name** through `instance.get_run_records(RunsFilter(job_name=...))`, so two code locations that both define a pipeline with the same name hold each other's ticks: a long run in one location silently skips the other location's schedule.

The limitation is accepted for now and documented in dag-tools AGENTS §4p. The workaround is to name pipelines distinctly across code locations.

The fix, when it is wanted, is to narrow the filter to the schedule's own code location: a `RunsFilter` on the location's repository tags, or a run tag the job stamps. The regression for it is a run of a same-named job in a *different* location that does not skip the tick, with the existing `test_a_started_run_of_the_job_skips_the_tick` as the control.
