### 5.2 HAZ-1003: the consumer is reached now; the audience has no actors

- The census row fails with disposition `drawn`, where the row accepts `task_requested`.
- cortex-bff logs `safety acceptance dispatched: hazard=HAZ-1003 level=Medium workflow=risk-acceptance-HAZ-1003-medium kind=risk_acceptance_medium`.
- Then **`POST /internal/human_tasks/register` → 422**, repeated. The caller is engine-a (`register_acceptance`).
- This is new: at rev 161 the register died with a 401 and never got this far. Mint-at-use works.
- `human_task_projection` still holds **0 rows** for `risk-acceptance-HAZ-1003-*`.

**Which 422.** I resolved the audience read-only inside cortex-bff with the gateway's own `_resolve_audience_actors`:

| audience | actors |
| --- | --- |
| `risk_acceptance_medium:SUSTAINMENT` | `[]` |
| `risk_acceptance_high:SUSTAINMENT` | `[]` |
| `access_grant:DATA_ENGINEERING` (control) | `['alice@example.com']` |

So the 422 is `no_entitled_recipients`.
- `policy/task_grants.yaml` has granted `risk_acceptance_medium:SUSTAINMENT` to bob since 2026-09-12.
- In sandbox `topazSeed.enabled: false`, so those grants never reached the live directory. This is bootstrap-state debt.
- The cell does not 422 on body validation: the control audience resolves through the same path. (The response body was not captured, so "422 = zero recipients" is inferred from the resolution, not read from the response.)

**The fix: a human executes it. The agent does not write the directory.**
- I computed `task_grant_sync`'s plan read-only against live Topaz: no `set_object`, no apply.
- The plan is **+8 actor relations, −0**. Six relations exist live and the plan keeps all six.
- The eight it adds: `risk_acceptance_{high,serious}` → alice; `risk_acceptance_{medium,low}`, `risk_redraft` and `hazard_link_review` → bob; `risk_acceptance_concurrence_{high,serious}` → carol.
- Command:
  ```
  kubectl -n sandbox exec deploy/iagent-cortex-bff -- sh -c 'cd /app && python policy/sync/task_grant_sync.py'
  ```
  Exit 0 means the readback resolved every grant.
- That seeds what git already asserts. The durable fix is an enabled seed or a bootstrap step: a sandbox whose task grants exist only after a hand-run sync will lose them again on the next fresh directory.

**A second defect this exposes (engine-a): a terminal 422 is retried forever.**
- `register_acceptance` (`agent_fleet/restate_analyst/main.py`) treats only 401/403 as `TerminalError`. A 422 goes through `raise_for_status()` and becomes retryable, so Restate re-runs the step indefinitely.
- That contradicts the gateway's own contract at the register route: "TERMINAL 4xx … the caller's workflow must fail-and-release (never park or retry-forever)".
- It also has one upside today: once the grants are seeded, the parked `risk-acceptance-HAZ-1003-medium` invocation should register on its next retry, with no re-fire. That is **not verified**.
- Routed to the architect for an owner. I did not fix it in this relay.
