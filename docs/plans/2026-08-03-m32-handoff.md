## SHIPPING THE DEFINITIONS — RULED 2026-08-04 (image-baked)

The builds surfaced a gap the packet did not have: **nothing loads the git-asserted
definitions at runtime.** `load_all_workflows` had zero non-test callers repo-wide,
and `policy/` reaches the cluster only as Topaz configmaps + the seed cronjob.
`_run_definition` had only ever run on a client-supplied `request["definition"]`.
The runtime registry now exists (`workflow_definition.get_workflow_definition`,
directory via `WORKFLOW_DEFINITIONS_DIR`, loud + specific when the definitions are
absent) — but the YAMLs still have to physically arrive in the pod.

**RULING: bake `policy/workflows/` into the image.** Three reasons:
  1. the gate tested executor-plus-YAML as ONE unit, and the deploy should ship the
     unit that was tested;
  2. definitions have no sync discipline the way Topaz configs do — no validate ->
     reconcile -> readback, no prune scope;
  3. hot-swap is a property these definitions should NOT have until they earn their
     own validation pipeline. A process you can change without a build is a process
     that changes without review.

**PROVENANCE, stated exactly.** This was decided 2026-08-04, in the session that
found the gap. It is NOT a pre-existing ratification — a claim that it had been
ruled earlier could not be sourced to this transcript or to any doc, and recording
an unfindable citation is the failure this packet's own amendment exists to prevent.
What DOES pre-exist is [ADR-0036](../adr/ADR-0036-config-layering-seed-overlay-composition.md)
(2026-08-03, "Accepted (pattern + composition site)", "No overlay exists yet"), whose
open question 3 asks *"Do workflow definitions overlay at all, or does work simply
author its own?"* and defers it "to the first work-authored workflow". This ruling
decides the BASE (image) and leaves OQ3 exactly where the ADR left it.

**NOT built, and deliberately so:** an ordered directory list with later-wins +
per-source load logging (the Topaz-style overlay shape). That is a real increment,
contingent on verifying the work deploy's mount support, and it belongs to whoever
closes ADR-0036 OQ3 — not to a registry that quietly grows the capability first.
