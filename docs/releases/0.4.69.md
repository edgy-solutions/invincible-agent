## What changed

The two releases carry chart changes only. Neither adds an image change to what the sandbox runs:
see "The sandbox runs it".

**0.4.68: `training-workbench`, a public login client (#90).**
- New `keycloak.publicClients`. Each client is public, PKCE S256, with literal https redirects.
  The render refuses a wildcard.
- The sandbox declares `training-workbench`, redirect `https://<training-host>/*`, which emits
  `authz_id`.
- The realm reconcile job creates the client if it is absent, repairs its mappers, and reads it
  back: `ok   training-workbench public, pkce S256, emits authz_id`.

**0.4.69: cortex-ui's redirects are literal (#91).**

**Finding: the `cortex-ui` client accepted any redirect.**
- Its realm import carried `redirectUris: ["*"]` and `webOrigins: ["*"]`, on a public client.
- Anyone who got a signed-in user to click a crafted login link could name their own redirect
  and collect the user's authorization code, and with it a token.
- The architect raised it on 2026-10-24. It is the shape `keycloak.publicClients` already refuses.

**The fix.**
- The set is `https://<host>` and `https://<host>/`, the web origin is `https://<host>`, and the
  post-logout redirect is `https://<host>/`, held separately.
- No deep-link paths: `/case/<id>` and `/ask?q=` ride in OIDC state, not in the redirect.
- New `keycloak.cortexUiClient` keys. When they are empty, the set derives from
  `cortexUi.ingress`'s TLS hosts.
- With no set, declared or derived, the import emits no redirect (fail closed). The job leaves
  the live client alone and prints `WARN cortex-ui: live redirectUris holds a wildcard`.
- The reconcile job converges a live realm. This is its one declared exception to additive-only.
  The readback line is meant to be `ok   cortex-ui redirects <n> literal, no wildcard`.
- **Defect, found by the roll:** both the readback and the converge check compare the redirect
  array as text. Keycloak serves it as a set, in its own order, so on the sandbox the readback
  printed FAIL on a correct realm, and the release failed. See "The sandbox runs it". The fix is
  #100.

**Work's realm needs the same fix.**
- It is fixed by this chart only if work's `cortexUi.ingress` lists its TLS hosts.
- Otherwise work must declare `keycloak.cortexUiClient`. Until then the job only warns, and the
  wildcard stays.

**Related, unchanged: cortex-ui keeps `directAccessGrantsEnabled: true`.** The sandbox walks and
the e2e harness sign in with the password grant. This release does not change it.

## Images

**Every `:0.4.69` tag now exists: 19 of 19.** The tags are on the images built from this release's commit, `7a45a3cb4b19137833398d0c50008d4a9be8f21f`. They were not there when the release was published. The repair under "Repair" below added them.

**What went wrong.** The release's retag ran in parallel with its build and finished first, so the published manifest listed all 19 images as missing. 0.4.66 and 0.4.68 lost the same race. The chart's image-tag floor is `Chart.Version`, so until the repair, any install that did not set `global.imageTag` would have failed to pull every fleet image.

**These images are this commit's images.** They carry every runtime change on master at `7a45a3cb`, not only this release's chart. That is correct: a release is its commit. What the sandbox runs is a separate decision, and it stays at `867813be` (see "The sandbox runs it").

## Repair

The race is fixed at its root in [#93](https://github.com/edgy-solutions/invincible-agent/pull/93), merged as `db7db75c`:
- The chart release is now a job of Build & Push, and it `needs: build` for the same commit.
- A missing image fails the release. It used to publish with a warning.
- A tag that already points at another digest is never overwritten. If one is found, the run stops and tags nothing.

Both broken releases were repaired by a logged `workflow_dispatch` of Release Helm Charts, never by hand:

| release | commit | dispatch run | tagged | already | missing | conflicts | verify |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0.4.68 | `aed0726ef4217f24dcad6de1645fb68457589520` | [40163650736](https://github.com/edgy-solutions/invincible-agent/actions/runs/40163650736) | 19/19 | 0 | 0 | 0 | passed |
| 0.4.69 | `7a45a3cb4b19137833398d0c50008d4a9be8f21f` | [40163755303](https://github.com/edgy-solutions/invincible-agent/actions/runs/40163755303) | 19/19 | 0 | 0 | 0 | passed |

How each dispatch ran:
- **It started by checking its sha.** The sha had to equal the commit its `invincible-agent-<version>` tag points to; otherwise the run would have stopped with nothing tagged.
- **It planned before writing anything.** For each image it read the existing `:<version>` tag, then tagged by digest only the images whose tag was absent.
- **It read every tag back.** The read-back also checks four controls, which must all fail: a fake digest, a short commit, an unpushed tag and a wrong digest.
- **It did not re-run chart-releaser.** It only replaced the release's `image-digests.json` asset.

The counts above were read from that asset after each run: `images` 19 against `expected` 19, with `missing`, `failed` and `conflicts` all 0.

**These tags never move again.** A later dispatch that finds a `:0.4.68` or `:0.4.69` tag at a different digest stops and reports. It does not overwrite.

## The sandbox runs it

**Helm revision 217 is marked `failed`, but the realm it wrote is correct.** The pods run 0.4.69's
chart, with the iagent images held at `867813be`.

**The roll.**
- It was rolled on 2026-10-25 from 09:37:07Z, under the roll lock, by `scripts/upgrade-sandbox.sh`
  at `7a45a3cb`.
- It went after the 07:00Z corpus gate. tr's readback had been pulled at 08:14Z, so no ingest was
  in flight, and the Dagster in-flight read was empty.
- At 09:44:10Z the post-upgrade hook `iagent-realm-reconcile` ended in `BackoffLimitExceeded`,
  and helm marked revision 217 `failed`.
- Revision 216 (0.4.67, 10-24) had also failed, on "keycloak never became ready". So the last
  revision marked `deployed` is still 215 (0.4.66).

**Why the hook failed.**
- The converge step replaced cortex-ui's `["*"]` with the two declared literals:
  `cortex-ui redirect set: converged (was ["*"])`.
- The readback then read back exactly those two, with no wildcard, but in the reverse order.
- It compares the array as text, so it printed
  `FAIL cortex-ui: live "redirectUris":[<b>,<a>] is not exactly "redirectUris":[<a>,<b>]`.
  It failed three times and stopped.
- The test double returned arrays in PUT order, so the suite could not see this. #100 compares
  the members as a set in both places, and makes the double serve the set fields reversed.

**What did not run.** `prime-substrate` and `engine-reregister` are ordered after the reconcile
hook, so neither ran on this revision. Engines register at startup in any case. The census below
reads the live registry.

**What the readback did say.** Every other line printed `ok`:
- `ok   training-workbench public, pkce S256, emits authz_id`;
- `ok   cortex-ui emits authz_id`;
- the OpenDDIL broker;
- the users, the retired users and the service accounts.

The only FAIL was the order compare above.
